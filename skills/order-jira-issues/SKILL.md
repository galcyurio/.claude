# Jira 이슈 순서 파악

## Overview

에픽 하위 이슈의 blocks 그래프를 뽑아 **지금 착수 가능한 것**과 **무엇에 막혀 있는지**를 보고한다. 막고 있는 것은 다른 이슈일 수도 있고, 서버 API 전달이나 디자인 에셋처럼 Jira 이슈가 아닌 것일 수도 있다. 둘 다 그래프에 나온다.

**핵심 원칙: 그래프는 스크립트가 뽑고, 코드까지 파고들지 않는다.** 순서는 Jira 링크와 PR·브랜치 상태로만 판단한다. 링크가 실제보다 보수적으로 걸려 있으면 그래프도 그만큼 보수적으로 나오므로, 착수 가능이 비어 보이면 링크부터 의심하고 그렇게 말한다.

## 언제 쓰지 않나

- 이슈 생성·분해·링크 설정·외부 의존 걸기 → `plan-feature-issues` (이미 걸린 외부 의존을 **해소**하는 것은 이 스킬의 2단계에서 한다)
- 단일 이슈 내용 조회 → 그냥 `getJiraIssue` (이 스킬을 도는 중에는 부르지 않는다. 설명은 스크립트가 이미 낸다)

## 절차

### 1. 그래프를 뽑는다 — 한 번의 호출로

```bash
python3 ~/.claude/skills/order-jira-issues/jira-deps.py HDA-22517
```

에픽이 아닌 대상은 `--jql "project = HDA AND labels = foo"`로 넘긴다.

Wave 레이어 그래프·임계 경로·이상 징후·열린 이슈의 설명을 한 번에 낸다 (이상 징후는 있을 때만 나온다). 맨 뒤의 `## 설명` 절은 착수 대상을 고를 때 쓰는 재료이므로 출력을 `head` 로 자르지 않는다. **이슈를 하나씩 조회해 손으로 그래프를 맞추지 않는다** — 그렇게 하면 12건짜리 에픽에 14회 호출과 12만 토큰이 든다(실측).

그래프는 이렇게 나온다. 의존 깊이별로 Wave 를 끊고, 노드 오른쪽에 blocks 대상을, 아래에 남은 blocker 를 붙인다.

```
Wave 1 ─ 막힌 것 없음 (착수 가능 1 · 진행 중 1)
  🟠 HDA-22530  모델 검색 API 연동 (진행 중) *             ─┬─▶ HDA-22554
                                                            └─▶ HDA-22561
  🟢 HDA-22538  퀵링크 DTO 추가                            ───▶ HDA-22554

Wave 2 ─ Wave 1 이후 (2건)
  ⛔ HDA-22554  MarketCarList 에 모델 퀵링크를 연결한다 *  ───▶ HDA-22570
       ▲ HDA-22530, HDA-22538, [디자인] 퀵링크 아이콘 자산 전달

외부 대기 ─ 다른 팀에서 와야 풀린다 (1건)
  ⛔ [디자인] 퀵링크 아이콘 자산 전달                      ───▶ HDA-22554
```

읽는 법:

- `Wave 1` 은 **미완료 blocker 가 없다**는 뜻일 뿐이다. 이미 진행 중인 이슈(🟠)도 여기 들어온다 — 헤더의 `착수 가능` 수만 지금 새로 잡을 수 있는 것이고, 병렬 후보는 🟢 노드뿐이다.
- `*` 는 임계 경로 위, `▲` 는 아직 안 풀린 blocker, `(?)` 는 조회 실패한 blocker다.
- `(에픽 밖)` 노드는 내 이슈가 아니다. Wave 헤더 건수에도 세지 않는다.
- `외부 대기` 절은 Jira 이슈가 아닌 blocker 다 — 서버 API 전달·디자인 에셋·기획 결정. 내가 잡을 수 있는 일이 아니라서 Wave 에 섞지 않고 따로 낸다. Wave 헤더 건수에도 세지 않는다. 해소된 것은 그래프에 나오지 않는다.
- `순환` 블록이 나오면 blocks 링크가 서로를 물고 있다는 뜻이다 — 링크를 고쳐야 한다.
- **완료 이슈는 그래프에 나오지 않는다.** 첫 줄의 `전체 N건`으로만 센다. 완료 이슈로 향하는 화살표도 지운다 — 이미 풀린 의존은 순서 판단에 쓰이지 않는다.

### 2. 실제 진행 상태를 교차 확인한다 — 이슈별이 아니라 한 번에

Jira 상태는 늦게 따라온다. 열린 이슈들의 실제 코드 쪽을 확인하되, 열린 키를 모아 **두 번의 호출로 전량을 받고 로컬에서 가른다**.

```bash
gh pr list --state all --search "HDA-22886 OR HDA-22888 OR HDA-22889 in:title" \
  --json number,title,state,headRefName,mergedAt
git ls-remote --heads origin "feature/*"
```

PR 은 `title` 에 키가 든 항목을, 브랜치는 `feature/<키>` 로 시작하는 줄을 골라 쓴다. `--json` 에서 `title` 을 빼면 어느 이슈의 PR인지 가릴 수 없다.

**이슈마다 따로 돌리지 않는다.** `git ls-remote` 는 호출마다 원격에 새로 접속해 2.3초씩 든다 — 열린 이슈 8건이면 두 명령이 23.8초를 먹지만, 위처럼 한 번씩만 부르면 3.0초에 끝난다(실측, 결과는 이슈별 조회와 동일).

**`in:title`을 빼면 오탐이 난다.** 검색어가 PR 본문에도 걸려서, `HDA-22538`로 찾으면 "HDA-22538에서 다룬다"고 적힌 다른 이슈의 PR이 나온다. 이미 된 줄 착각하게 만든다. 위 검색에서 안 나오면 PR이 없는 것으로 본다.

**외부 의존은 `git`·`gh`로 확인할 수 없다.** 외부 의존 노드의 근거 URL(요청 스레드·시안)을 열어 실제로 전달됐는지 본다. 이미 왔는데 그래프에 남아 있으면 해소를 제안한다.

```bash
python3 ~/.claude/skills/order-jira-issues/extdep.py list --epic HDA-22517
python3 ~/.claude/skills/order-jira-issues/extdep.py resolve --epic HDA-22517 --slug <slug>
```

`resolve` 는 사용자에게 확인받고 실행한다. `resolved` 는 "전달을 확인했다"는 뜻이라 상대 팀 이슈가 닫혔다는 것만으로는 근거가 되지 않는다.

읽는 법:

- PR이 머지됐는데 이슈가 Backlog → 그래프가 실제보다 비관적이다.
- 브랜치가 원격에 없다 → 아직 push 전. 그 이슈에 막힌 것들은 당분간 안 열린다.
- **브랜치가 원격에 있고 PR이 열려 있다 → 그 위에 스택해서 지금 착수 가능으로 본다.** 머지를 기다릴 이유가 없다. 다만 리뷰에서 API가 바뀔 수 있다는 점을 함께 말한다.

### 3. 보고한다

**그래프가 본문이고 결론은 맨 아래다.** 결론을 위에 두면 그래프에 밀려 화면 밖으로 나가고, 사용자가 스크롤을 올려야 한다.

순서대로:

1. **그래프** — 스크립트가 낸 `## 그래프` 블록을 **코드블록에 그대로** 붙인다. 요약해서 다시 쓰지 않는다. 정렬이 표시 폭 계산에 맞춰져 있으므로 코드블록 밖에 두면 어긋난다
2. **이상 징후** — 스크립트가 짚은 것만. 없으면 이 항목을 아예 쓰지 않는다
3. **외부 대기** — 외부 의존이 있으면 무엇을 누구에게 기다리는지 한 줄. 없으면 이 항목을 쓰지 않는다
4. **결론 2~3줄** — 지금 착수할 것 하나와 병렬 후보. 임계 경로 위에 착수 가능한 노드가 있으면 그것을, 없으면 blocks 대상이 가장 많은 것을, 그것도 같으면 키가 빠른 것을 고른다. 이슈 키는 `https://prndcompany.atlassian.net/browse/KEY` 링크로 건다

2단계에서 확인한 근거는 결론에 한 줄로 녹인다. 스크립트가 낸 `## 설명` 절은 착수 대상을 고를 때 참고만 하고 보고에 옮기지 않는다. 조사 과정을 나열하지 않는다. 그래프 앞에 서론을 쓰지 않는다.

## acli 함정

베이스라인 테스트에서 실제로 걸린 것들이다. 스크립트를 안 쓰고 직접 조회할 때만 필요하다.

| 하려던 것 | 결과 | 대신 |
|---|---|---|
| MCP `searchJiraIssuesUsingJql`로 `issuelinks` 받기 | 응답이 잘리는데 `hasNextPage: false`, `endCursor: null` — 페이징 불가 | 키만 받고 이슈별로 `view` |
| `fields`를 줄여 응답 축소 | `description`은 요청 안 해도 항상 붙는다 | 위와 동일 |
| `acli workitem search --fields "...,issuelinks"` | `✗ Error: field 'issuelinks' is not allowed` | `acli workitem view KEY --fields "...,issuelinks" --json` |
| `acli workitem search --fields "key" --json` | `[null, null, ...]` | `acli workitem search --csv` |
| `acli workitem link list --json` 파싱 | 배열 키가 `links`가 아니라 `issueLinks` | `d["issueLinks"]` |
| `acli workitem link delete --json` | `unknown flag: --json` | `--id ID --yes` (출력은 텍스트) |

## 흔한 실수

- **상태 이름으로 완료를 판정한다.** `종료`·`Ready to Deploy`·`Deployed`가 뒤섞여 있다. `status.statusCategory.key == "done"`으로 본다.
- **완료된 blocker를 blocker로 센다.** 완료 이슈가 무언가를 blocks 하는 것은 정상 이력이다. 막고 있는 것으로 치지 않는다.
- **종료된 이슈에 남은 링크를 그래프에 넣는다.** 대기 목록이 실제보다 길어 보인다.
- **임계 경로를 빼먹는다.** 어느 이슈가 병목인지가 "다음에 뭘 할까"의 답이다.
- **그래프를 말로 풀어 요약한다.** 구조는 그림으로 봐야 빠르다. 스크립트 출력을 그대로 붙이고, 해석만 덧붙인다.
- **결론을 맨 위에 둔다.** 그래프가 길면 결론이 화면 밖으로 밀린다. 착수할 것은 마지막에 쓴다.
- **링크에 없는 근거를 코드에서 찾는다.** 이 스킬은 그래프와 PR·브랜치 상태까지만 본다. 소스 파일을 열거나 `getJiraIssue` 를 부르기 시작하면 끝나지 않는다 — 그러다 두 번 중단된 적이 있다(실측).
- **전달을 확인하지 않고 해소 처리한다.** `resolved` 는 사람이 전달을 확인했다는 뜻이다. 상대 팀 이슈가 완료로 바뀐 것은 개발이 끝났다는 뜻일 뿐 전달됐다는 뜻이 아니다.
