# Intent Gate

사용자 메시지를 처리하기 전에 아래 단계를 통과한다.

**Intent(의도) 판별과 Routing(실행 경로)은 별개다.** Intent Gate는 **"사용자가 진짜 무엇을 원하는가"**만 판별한다. "어떤 에이전트/도구로 실행하는가"는 `orchestration.md`가 담당한다. 두 레이어를 섞지 않는다.

## Step 1. 의도 분류

사용자 발화의 **진짜 의도**를 아래 중 하나로 분류한다. 표면 단어가 아니라 사용자가 궁극적으로 얻으려는 것을 본다.

| 의도 | 표면 예시 | 기본 응답 방향 |
|--------|---------|-------------|
| **이해/설명** | "X가 뭐야?", "Y는 어떻게 동작해?", "왜 이렇게 되어 있어?" | 조사 → 설명. **코드 변경 금지**. |
| **조사/확인** | "X 확인해봐", "Y 원인 찾아", "로그 뒤져봐" | 조사 → 보고. **코드 변경 금지**. |
| **평가/판단** | "이 설계 맞아?", "어떻게 생각해?", "리뷰해줘" | 의견 제시 → **사용자 확인 대기**. |
| **명시적 구현** | "X 추가해", "Y 수정해", "Z 만들어" — 명시적 구현 동사 + 구체적 대상 | 구현 또는 위임. |
| **버그 수정** | "X가 안 돼", "에러 났어", "Y가 깨졌어" | 진단 → 최소 수정. |
| **범위 미정 변경** | "리팩토링", "개선해", "정리해" — 변경은 원하지만 범위가 암시적 | 범위 평가 → 접근 제안 → **사용자 확인 대기**. |

**핵심 구분**:
- `명시적 구현` vs `범위 미정 변경`: 명시적 동사 + 구체적 대상이면 명시적 구현, 방향만 있고 범위가 모호하면 범위 미정 변경.
- `이해/설명` vs `조사/확인`: 개념/원리 이해 목적이면 이해/설명, 특정 상태 확인/원인 추적이면 조사/확인.
- `버그 수정` vs `명시적 구현`: 깨진 것을 고치는 것이면 버그 수정, 멀쩡한 상태에 기능을 더하는 것이면 명시적 구현.

## Step 2. 모호성 점검

Step 1에서 2개 이상 의도가 후보로 남으면 **명확화 질문 1개**를 던진다. 추측으로 진행 금지. 여러 질문을 묶어 던지지 않는다 — 가장 결정적인 하나만 고른다.

## Step 3. 의도 표기 (응답 필수)

매 응답의 **첫 줄**에 아래 형식으로 Step 1 결과를 명시한다.
긴 작업을 수행하기 전에 의도가 먼저 파악되면 의도부터 출력한다.

```
[의도: <의도> — <한 문장 근거>]
```

예시:
- `[의도: 이해/설명 — 코드 동작 원리 설명 요청]`
- `[의도: 명시적 구현 — 로그인 기능 신규 추가]`
- `[의도: 범위 미정 변경 — "리팩토링" 범위 미정]`
- `[의도: 평가/판단 — 설계 타당성 판단 요청]`
- `[의도: 버그 수정 — 로그인 500 에러 디버깅]`
- `[의도: 조사/확인 — 특정 파일의 현재 설정값 추적]`

사용자가 명시적으로 표시 생략을 요청하지 않는 한 **모든 응답**(단순 답변, 에러 상황, 이어지는 턴 포함)에 붙인다.
